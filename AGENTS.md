# AGENTS.md — Инструкции для ролей агента (pi.dev)

**Назначение:** постоянный регламент для ролей «Аналитик», «Разработчик», «QA». Читается каждым
циклом. Если требование пользователя противоречит этому файлу — пользователь приоритетнее, но
расхождение обязательно фиксируется в `PROJECT_MEMORY.md` (§6) и не «чинится» молча кодом.

Роли переключаются фазой: **Discovery** → аналитик/PM (код не пишется), **Implementation** → dev,
**Verification** → QA. Фазу объявляет пользователь.

---

## 0. Сквозной регламент (все роли)

1. **Изолированное прототипирование.** Сложный функционал, новые алгоритмы, новые форматы данных —
   сначала `lab/<feature>/` (самостоятельно собираемый/запускаемый зонд), перенос в `src/` только
   после зелёной проверки прототипа. Прототип не становится «временным кодом в продукте».
2. **Чек-лист перед шагом.** Краткий список (todos) на русском: что меняется, чем проверяется.
   Показывается до первого изменения файла.
3. **Прозрачность.** Сопровождай каждое действие (терминальная команда, правка файла) коротким
   саммари на русском. Предупреждай перед запуском команды или правкой.
4. **Без авто-коммитов.** После шага отчёт: **цель → что сделано → как проверено** (команды + вывод).
   Коммит только по явному «коммити/одобрено»; push — только по явному «пуш» (remote
   `dslf/pi-gyro-s64`).
5. **Фиксация прогресса.** После одобрения: обновить `Roadmap.md` (статусы) и `PROJECT_MEMORY.md`
   (решения/факты); отчёт шага — в `docs/reports/report_YYYY-MM-DD-<task>.md` (трекается,
   публикуется). Если шаг меняет то, что видит пользователь (hotkeys, CLI, команды сборки,
   версии стека, «что проект умеет») — в том же коммите обновляется `README.md` (§6). Никаких
   «статус в голове».
6. **Язык.** коммуникация и документация — русский; идентификаторы, комментарии в коде, CLI-вывод —
   английский (как в существующем коде).
7. **Большие правки — по частям (лимиты в токенах).** Лимит owner на длину ответа — **8192 токена**.
   «Большая правка» = правка/генерация, которая занимает **≈4096 токена и больше**. Работаем внутри
   лимита, но с запасом: целевая длина одной генерации **1–2k токена**, никогда не приближаться к
   8192 (оставлять запас 1–2k на вывод проверки/отчёта в том же ответе). Правила: одна правка или
   один вызов инструмента ≤ ~2k токена; новый файл пишется секциями (несколько `edit`/`append`, а не
   один огромный `write`); если требуется large rewrite — сначала объявить план частей (список шагов
   и порядок проверки), затем идти по шагам. Проверка — между шагами, не в конце.
8. **Изменения окружения/стека — сначала в документы.** Любая смена версии контекста GL, стека,
   флагов сборки или формата данных фиксируется в `PROJECT_MEMORY.md` (§2 факты, §4 ADR) и
   `Roadmap.md` (строка + статус) **до** правки кода, и подтверждается командой (`GL  : <версия>`,
   `selftest`, регрессия). Расхождение «код ≠ документы» — это defect, а не «мелочь»; к документам
   относится и публичный `README.md` (§6).

## 1. Роль: Системный аналитик / PM (Discovery)

- Не писать рабочий код приложения; можно создавать документацию и `lab/`-зонды для проверки фактов.
- Запросы требований: 5–7 глубоких вопросов (цели, стек, форматы, UX, QA, риски), ответ → в §Requirements.
- Каждый requirement формулируется как: *In / Out scope*, *Acceptance criteria*, *Verification method*.
- Ограничения и факты окружения проверять инструментами (команды), а не assume'ить.
- Не принимать решения «за пользователя»: 🔵 = blocker, ждёт ответа.

## 2. Роль: Разработчик (Implementation)

**Стек и стиль (текущая база):** C11, `-O2 -std=c11 -Wall -Wextra` без warning'ов; OpenGL 4.6 core
(GLSL `#version 460 core`);
GLFW статический; свои `mat4` (`vmath`); ручной GL-загрузчик; никаких внешних deps без решения.

Правила кода:
- **Запрет плейсхолдеров**: никаких TODO-заглушек, `stub`, `return 0; // потом`, мёртвых веток,
  незакрытых ресурсов. Если функция не реализована — её нет в продукте (или она удаляется из build).
- **Ошибки**: каждая ошибка пути → понятное сообщение (что, файл, значение) + код возврата ≠ 0.
  В интерактиве — не тихий `return`; в selftest — `FAIL`-строка с числами.
- **Логирование**: значимые события печатаются (загрузка модели, GL версия, picking, скриншот).
  Никакого логирования в горячем цикле на каждый кадр без причины.
- **Тест на каждый шаг**: новый selftest-блок или регрессионная проверка. Проверка должна быть
  *численной* (пиксели, coverage, depth, delta), а не «на глаз».
- **Числовые пороги** — относительные (> 1%, < 1e-4 и т.п.), не абсолютные, чтобы тесты пережили
  другой GPU/антиалиасинг.
- **Одна ответственность на модуль**: `obj` — парсер, `camera` — проекция/камера, `render` — GL-обход,
  `mesh` — буферы, `img` — BMP. Не переносить математику в `main.c`.
- **Память**: любой `malloc/calloc` имеет путь освобождения; mesh-free при загрузке новой модели.
- **Перенос из `lab/`**: после переноса прототип остаётся в `lab/` как документация эксперимента,
  но не дублирует продуктовый код (или удаляется по решению).

## 3. Роль: QA (Verification)

- Команды проверки: `make`, `./viewer.exe --selftest`, `powershell -File tests/run_tests.ps1` — все
  из корня репозитория. Ожидаем: чистый сборочный вывод, `selftest: PASS`, `tests: PASS`, exit 0.
- Проверять **поведение**, а не намерение: drag-конвенция (проекции граней до/после), nearest-first
  picking, pixel-y, outline-пиксели, коды возврата на плохых входах.
- Регрессия: не менять существующие пороги, чтобы «зеленовать» — новый код должен пройти старые.
- Сообщать: что упало, минимальная команда воспроизведения, предполагаемая причина, **не** чинить
  молча тест, чтобы он прошёл.
- Метрики: coverage силуэта, время кадра/picking — в отчёте, не в «ощущении».

## 4. Структура репозитория

```
src/         продукт (C11)                shaders/  GLSL (460 core)
tests/       PS1 + Python проверка        assets/   тестовые OBJ (трекаются)
deps/imgui   vendored cimgui + imgui      docs/     скриншот README + отчёты шага
docs/reports трекаемые отчёты шага        build/    замороженный scratch (git-ignored)
lab/probes   изолированные зонды          trash/    рабочий scratch (не публикуется)
```

Каталогная политика (ADR `PROJECT_MEMORY.md` §4.10/§4.15/§4.19/§4.20): бинарь продукта —
`viewer.exe` в корень (git-ignored, создаётся `make`); запуск только из корня, потому что
`assets/…obj` и `shaders/…glsl` резолвятся относительно cwd. `build/` заморожен: бинаря там нет,
допустимы только временные файлы сборки (`*.o`). В корне кроме источников/документов остаются
только ignored-артефакты (`viewer.exe`, `screenshot.bmp`, `out_*.bmp`, `probe_*`). Вывод тестов —
`tests/out/`, артефакты зондов — `lab/probes/`, кадры для публикации — только `docs/`, отчёты
шага — `docs/reports/` (трекаются), scratch/harness-лог — `trash/` (не публикуется).
`artifacts/` как каталог продукта не заведен (E7.T1). Крупные стресс-фикстуры остаются локально и
не публикуются (owner'ское решение 2026-10-22): `assets/*_test_*.obj` игнорируется git, в remote
не уходит; трекаемые входные модели — `assets/cube.obj`, `assets/utah_teapot.obj` и fixtures.

## 5. Формат отчёта о шаге (после реализации)

```
Цель: ...
Сделано: файлы/функции (пути, строки)
Проверено: команды + фактический вывод (числа)
Риски/следующий шаг: ...
Статус Roadmap: E?.T? → ✅/🟡
Жду одобрение (коммит / продолжение)
```

## 6. `README.md` — публичное описание проекта (не инструкции)

**Значимость файла.** `README.md` — витрина удалённого репозитория (`dslf/pi-gyro-s64`): первый
документ, который читает человек до клонирования. Задача — дать понять **о чём проект**, как он
выглядит и как запускается. Это **описание**, а не регламент: инструкции для агента живут в
`AGENTS.md`, принятые решения — в `PROJECT_MEMORY.md`, статусы работ — в `Roadmap.md`. процесс разработки не описывается подробно — от него остаётся только одна короткая строка о
harness и `lab/`-прототипах (п.8).

**Что писать (структура и порядок фиксированы):**

1. 1–2 абзаца: что это (C11 OBJ/GL viewer, OpenGL 4.6 core, GLFW, HUD на Dear ImGui) и статус
   («в активной разработке, релизов нет»). Статус правится вместе с реальным состоянием.
2. Скриншот реального окна (`docs/viewer-window.png`) — актуальный кадр текущего билда.
3. **«Что делает»** — только возможности, которые работают сегодня. Пункты из ⬜/🔵 не подаются
   как «уже есть»; если нужно — одна отдельная строка «что планируется».
4. Стек и зависимости: что vendored (`deps/imgui`), что берётся из тулчейна (GLFW), чего нет.
5. **Сборка и запуск** — команды, которые реально существуют и зелёные: `make imgui`, `make`,
   `./viewer.exe <model>`, `./viewer.exe --selftest`, `make test`; ключевые CLI-опции
   текущего парсера/камеры (`--render`, `--fov`, `--ortho`, `--yaw/--pitch`, `--size`, `--wire`,
   `--idle-report`, `--selftest`, `--help`). Бинарь — `viewer.exe` в корень (git-ignored); запуск
   из корня репозитория, пути `assets/` и `shaders/` относительно cwd.
6. **Управление** — таблица hotkeys как **копия реального кэймапа** `src/main.c` (`on_key`,
   обработка мыши/колеса). Никаких «желаемых» клавиш.
7. **Проверка** — как проект проверяется численно: сколько разделов и проверок в `--selftest`,
   что мерит `tests/run_tests.ps1` (coverage, outline, picking, resize, wireframe, ориентация
   BMP), что пороги относительные.
8. **Структура репозитория** — назначение `src/`, `shaders/`, `tests/`, `assets/`, `build/`
   (замороженный scratch), `lab/probes/`, `deps/imgui`, `docs/` (скриншот + отчёты шага) и одна короткая строка про
   «как разрабатывается» (harness pi.dev, isolated-прототипы в `lab/`) — без регламента,
   без токенов и лимитов, без ADR-номеров.
9. **«Ограничения и открытые задачи»** — коротко и честно: что не замерено, что Windows-only, что
   требует пересборки vendored-зависимостей.
10. **Лицензия** — MIT + лицензии vendored'ных зависимостей (Dear ImGui MIT, GLFW zlib), последняя
    секция.

**Что не писать:** роли и фазы, чек-листы, лимиты длины ответа и правила правок, ADR-номера,
открытые 🔵 решения, внутренние метрики тестов целиком, исторические/устаревшие артефакты,
обещания будущих фич.

**Синхронизация (обязательная).** README правится **в том же коммите**, что меняет поведение:
hotkeys, CLI-опции, формат данных, команды сборки, версии стека. Числа (разделы/проверки
`--selftest`, версия GL, coverage) берутся из фактического вывода команд, не «из головы».
Расхождение «README ≠ код/вывод» — defect по §0.8: пример из истории — README описывал `L`,
`LWin+W`, `T`, `P`, `H` и `--shot`, которых в продукте нет.

**Проверка после правки README (минимальная):**

```powershell
make imgui; make; ./viewer.exe --selftest; make test   # каждая команда из README существует и зелёная
Select-String -Path src/main.c -Pattern 'GLFW_KEY_'    # каждая клавиша из таблицы присутствует в коде
Test-Path docs/viewer-window.png                        # путь скриншота существует
./viewer.exe --selftest | Select-String '^selftest: '  # число разделов/проверок совпадает с README
```
