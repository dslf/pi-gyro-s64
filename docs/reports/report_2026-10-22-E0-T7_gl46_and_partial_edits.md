перейти на OpenGL 4.6 core и зафиксировать правило: большие правки делаются частями.

## Риски / следующий шаг

- `gl.c` грузит функции через `glfwGetProcAddress` → `wglGetProcAddress` → `opengl32.dll`.
  В compat-контексте 4.6 последний путь для GL 1.1-функции даёт generic-реализацию — продуктовый
  путь подтверждён пикселями, но зонды с hidden-window остаются ненадёжными для diagnostics.
- 4.6 compat (не forward-compat) допустим: deprecated-функции в продукте не используются;
  при переходе на forward-compat нужно убрать все legacy-вызовы (проверка отдельно).
- Продолжение предыдущего шага: перенос HUD в продукт (`src/hud.c` + атлас глифов) — идёт
  маленькими шагами по новому регламенту.

## Уточнение owner (E0.T8, лимиты в токенах)

Жёсткий лимит длины ответа — **8192 токена**. «Большая правка» = правка, которая занимает
**≥ 4096 токена**. Работаем внутри лимита с запасом: целевая длина одной генерации **1–2k токена**,
запас 1–2k держится постоянно (на вывод проверки и отчёта). Large rewrite как один вызов запрещён:
новый файл — секциями через `edit`/`append`, правки — последовательными шагами, проверка между
шагами, план частей объявляется до первой правки. Формулировки обновлены в `AGENTS.md` §0.7,
`PROJECT_MEMORY.md` §4.11, `Roadmap.md` E0.T8 (коды и шейдеры не менялись — сборка и тесты
остаются зелёными: ok=26 / ok=59, fail=0).
